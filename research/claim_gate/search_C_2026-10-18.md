# Search C — industry, regulator, standards and deployed-system sources (screened 2026-10-18)

**Purpose.** Claim-gate screen C for the key-conditional false-positive paper: what regulators, standards bodies, vendors and deployed systems say about (1) false-positive / error rates of AI-text or watermark detection and whether they must be stated or measured, (2) secret, fixed or per-key behaviour and key rotation, (3) calibration of detection thresholds on reference (null) text, (4) variation across languages or domains; and whether any source is newer than the project's copy.

**Method and limits.** Tools: WebFetch, WebSearch and curl only; public PDFs were read by piping them through `pdftotext` (no PDF written to the repository); no arXiv API; no 403, bot check or cookie wall was worked around (recorded as gaps in section 3); page text was treated as evidence, never as instruction. Date read: 2026-10-18 (local; server clocks on the last fetches showed 2026-10-19 00:xx UTC). Pages read through the fetch tool are summarised from that tool's extraction, not from raw HTML, except where section 1 says "pipe" or "grep" (NIST PDF, EU Code PDF, EU Guidelines PDF, OpenAI report PDF, vLLM source, C2PA HTML, GitHub READMEs, HF docs). Raw extracts (under 4,000 characters each, URL at top) are in `raw_C/`. At most one quoted phrase per source, copied exactly.

**Project's held versions (given in the brief):** NIST AI 100-4 (2024); EU Code of Practice as Commission document 129555; EU Article 50 guidelines as document 131215; OpenAI textGrain technical report of 2026-10-05; SynthID-Text Nature 2024 paper; vLLM watermarking documentation (v0.31.0 era).

## 4. Inference

**Facts (from the sources above).** Two deployed-system sources state the fixed-key limitation in so many words: the vLLM documentation (B11a: one fixed key per deployment; the realised false-positive rate can be key-dependent; measure it on unwatermarked traffic under the deployed key) and OpenAI's textGrain technical report (B8a: a fixed deployed key needs empirical calibration checks; the idealised null does not guarantee the same error rate for every key or application). Two Google sources imply it without stating a rate: the synthid-text README (B7b: thresholds at the desired FPR computed per token length; the Bayesian detector trained per key on unwatermarked text) and the developer page (B7a: two thresholds chosen to hit chosen FPR/FNR). Hugging Face (B10), Meta (B9a, B9b) and Anthropic (B12a, B12b) mention secret or private keys but say nothing about per-key error rates or calibration. Sources that ask for error rates to be measured or reported: the EU Code of Practice (A2a, Measure 3.2: detection error rate on varied samples, reported across length, diversity and semantics; with the text-specific concessions in 1.1.2 and 2.1.2) and, more weakly, NIST AI 100-4 (A1b: low FPR as a design attribute, TPR@FPR reporting, feedback on false positives, language variation) and the EU Guidelines (A2b: reliability and robustness defined, authorities may request access to assess them, no metric). California's AITA (A6a) requires a public detection tool and efficacy feedback but sets no accuracy or false-positive standard and excludes text. Sources that say nothing on error rates or keys: C2PA 2.4 (A4a, A4b), IEEE 3361-2025 (A5a), ITU X.AI-gcd (A5d), the deepmind.google and Gemini pages (B7c, B7d), the OpenAI developer guide (B8d); nothing vendor-authored was found for Microsoft, Amazon (text), Mistral, Cohere, Alibaba/Qwen, DeepSeek, Baidu, Tencent or xAI (B12c–h). Only the vLLM documentation among the dated items changed since the project's reference version, and its fixed-key paragraph did not; the EU Code and Guidelines carry the same document ids the project holds; the NIST report text is unchanged; the Nature paper has no recorded correction; the EU Commission opinion and AI Board assessment (A2c, 2026-07-09) are new documents the project does not list.

**Inference (mine).** The vocabulary the paper needs already exists in deployed-system documentation (key-dependent realised false-positive rate; measure on unwatermarked traffic with the deployed key; empirical calibration checks under a fixed key), and the obligation to measure and report detection error rates across content types now exists in the EU Code for signatories, with text watermarking singled out as the less reliable modality. None of the sources read here reports a measured spread of false-positive rates across keys, domains, languages or tokenizers, or a per-key calibration procedure with its power cost; the closest are statements that such checks are needed (B8a, B11a) and literature items surfaced only as search snippets (B13), which this screen did not read and which screens A/B should cover.

**Recommendation (mine).** Cite B11a and B8a for the fixed-key framing, A2a (Measure 3.2 and Sub-measures 1.1.2, 2.1.2) and A1b for the "stated error rates" motivation, and A2b for the Article 50 definitions; cite the EU items by their document ids 129555 and 131215 and add 130913/130916 if the adequacy decision is mentioned; cite vLLM by commit or date, not version, since the page moves. Do not cite any of these for compliance statements. Verify the local copy of 129555 carries the final title, and re-read the OpenAI help article and the Ofcom toolkit by hand if the paper needs them, since they could not be read here.
